# Initial Direct3D 12 display, bitmap and clipping path

The Windows-only `nexaui_renderer_d3d12` target is a private D01–D07 component.
It borrows the Win32 window's `HWND` through a private thread-checked adapter;
the public `nx_window` API still exposes no native handle. The window must
outlive the renderer, and creation, rendering, resize and destruction all run
on the window's creation thread.

The renderer creates a DXGI factory, an ID3D12Device at feature level 11_0,
a direct command queue, a three-buffer flip-discard swap chain, an RTV heap,
one allocator per back buffer, one reusable command list and a fence. It tries the default adapter first and
uses DXGI WARP if device creation fails. This follows Microsoft's
[basic D3D12 component sequence](https://learn.microsoft.com/en-us/windows/win32/direct3d12/creating-a-basic-direct3d-12-component)
and [WARP guidance](https://learn.microsoft.com/en-us/windows/win32/direct3d12/porting-from-direct3d-11-to-direct3d-12).
The flip-model description uses one sample and at least two buffers as required by the
[DXGI swap-chain contract](https://learn.microsoft.com/en-us/windows/desktop/api/dxgi1_2/ns-dxgi1_2-dxgi_swap_chain_desc1).

`nx_d3d12_clear_present` reads the current physical client size. A zero-size
client skips submission. On a changed size, the renderer waits for its
previous GPU work, releases the back-buffer references, calls `ResizeBuffers`
and rebuilds RTVs. Each frame transitions the current buffer from PRESENT to
RENDER_TARGET, clears it, transitions back, executes the list and presents.
The buffer must be in PRESENT state for presentation, per the
[D3D12 swap-chain rules](https://learn.microsoft.com/en-us/windows/win32/direct3d12/swap-chains).
Opaque and empty frames use one allocator and vertex upload ring per back-buffer
slot. A fence limits the CPU to two submitted frames before it waits for the
older one; a slot cannot be reset or overwritten until its own fence completes.
Bitmap and translucent frames still wait for all earlier work before reusing
their shared upload buffer, descriptor heap and compositing texture, then wait
for the submitted frame to finish. Resize and teardown also wait for all work.
This follows Microsoft's [allocator reset contract](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12commandallocator-reset)
and [fence-based resource management](https://learn.microsoft.com/en-us/windows/win32/direct3d12/fence-based-resource-management).

The F11 adapter draws filled, stroked and rounded rectangles, filled triangles
and round-capped lines in paint order, with nested `PUSH_CLIP` and
`POP_CLIP` commands. It compiles an embedded HLSL vertex
and pixel shader on the first geometry frame, creates an empty root signature
and triangle PSO, expands rectangles into two triangles, applies the target's
backing scale, and writes vertices into the current slot's growable upload ring.
Colors are rounded to RGBA8 before the shader to match the headless source-color
conversion. The ring is reused only after its fence completes. A stroked
rectangle uses four non-overlapping strips, or one filled rectangle when its
stroke consumes the interior. Lines and rounded rectangles use bounding quads
and a pixel shader that checks each pixel center against the segment or corner
radius.
Adjacent opaque rectangles, strokes and triangles with non-overlapping bounds share draw calls in batches
of at most 64 commands; overlaps and clips flush the batch to preserve paint
order. This follows the
[D3D12 pipeline setup](https://learn.microsoft.com/en-us/windows/win32/direct3d12/creating-a-basic-direct3d-12-component).
Each clip intersects its parent and becomes a D3D12 scissor for the next draw.
The clip edges use the same pixel-center rule as the headless renderer, including
fractional coordinates and backing scale. Opaque primitives use the ordinary
pipeline. For partial alpha, a second pixel shader reads a copy of the current
back buffer and applies the headless integer RGBA8 blend formula. This also
handles transparent and partially transparent clear colors. Each translucent
shape or bitmap copies only its clipped, conservatively expanded bounds into
the previous-color texture. Adjacent translucent rectangles, strokes and triangles with
non-overlapping bounds share one copy and draw for up to 64 commands. Their
copy region is the union of the clipped shape regions, so a scattered batch
can transfer more texels than separate copies. Overlaps, clip changes, opaque
draws, lines and bitmaps flush the batch to preserve paint order. Lines and
bitmaps still use one copy and draw each. D3D12
[scissor rectangles](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-rssetscissorrects),
[texture-region copies](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12graphicscommandlist-copytextureregion)
and [shader-visible descriptors](https://learn.microsoft.com/en-us/windows/win32/direct3d12/shader-visible-descriptor-heaps)
provide the GPU operations used here.

`NX_COMMAND_BITMAP` accepts RGBA8 images and A8 glyph masks. The renderer
deduplicates identical source views within one frame, stages each distinct view
into a shared row-pitch-aligned upload buffer before submission and copies it
to a GPU texture. A growable shader-visible heap holds two descriptors for each
distinct view. A bounded pool retains up to 256 textures and 64 MiB of texture
allocations for reuse in later frames; excess textures are transient until the
frame fence completes. Source contents are uploaded again on each frame, so
mutations of borrowed image data are visible. The
pixel shader loads the nearest source texel, applies RGBA8 tint multiplication
or A8 coverage multiplication, then uses the same integer straight-alpha
compositing formula as the headless renderer. It reads a copy of the current
back buffer so source alpha may vary across the bitmap. This follows D3D12's
[texture upload and row-pitch rules](https://learn.microsoft.com/en-us/windows/win32/direct3d12/upload-and-readback-of-texture-data),
[shader-resource view contract](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12device-createshaderresourceview)
and [resource-state transitions](https://learn.microsoft.com/en-us/windows/win32/direct3d12/using-resource-barriers-to-synchronize-resource-states-in-direct3d-12).

Three timestamp queries per frame slot mark the start of GPU work, the end of
texture uploads and the end of rendering. The command list resolves them into
that slot's small readback buffer. `nx_d3d12_renderer_get_info` reads only
completed slots after their fences and reports the latest completed GPU upload,
render and total durations, plus the queue timestamp frequency and frame ID.
An asynchronous frame may therefore report an earlier frame until its fence
completes. Query creation is optional; zero frequency means timing is
unavailable. These timestamps exclude `Present`, CPU command preparation and
the private pixel-readback copy. See Microsoft's [D3D12 timing contract](https://learn.microsoft.com/en-us/windows/win32/direct3d12/timing).

The renderer checks failed D3D12/DXGI calls and the completed fence value for
device removal. A lost device stops further direct submissions. Through the
F11 adapter it reports `NX_RENDER_DEVICE_LOST`; `nx_renderer_recover` releases
all old device, queue, list, fence, descriptor and swap-chain objects and
creates replacements before the driver resumes. A failed rebuild leaves the
driver lost so the caller may retry. The direct private API exposes the same
operation as `nx_d3d12_renderer_recover`. Microsoft documents
[device removal and recreation](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/dxgi-error)
and the [removed fence sentinel](https://learn.microsoft.com/en-us/windows/win32/api/d3d12/nf-d3d12-id3d12fence-getcompletedvalue).

The F11 adapter `nx_d3d12_driver_open` accepts the full current core command
stream: filled, stroked and rounded rectangles, filled triangles, lines,
RGBA8 images, A8 glyph masks and nested clips. A hidden-window native smoke test
creates the device, submits six clears, changes the Win32 size and verifies the
renderer reports a larger target and the expected submission count. On systems
with `ID3D12Device5`, the test forces actual device removal and verifies direct
and F11 recovery followed by another successful submission. A test-only
partial rebuild failure checks that recovery can be retried. The visible
[native geometry example](../../examples/10_native_clear/README.md) opens a
window for three seconds. The test copies the GPU back buffer into a readback
buffer before presenting and compares every RGBA8 byte with the headless
renderer at 1× and 2× scale, then repeats with fractional/offscreen geometry
and with two half-alpha shapes on opaque, transparent and partially transparent
targets. Nested and fractional clips are checked at 1× and 2× scale. The
test also compares RGBA8 images, A8 masks, a mask produced by NexaUI's glyph
rasterizer, padded source rows, per-pixel alpha and source-data changes. It
repeats bitmap rendering after resize and device recreation. Further tests
compare 1,000 opaque rectangles, 128 distinct images and a 260-image pool
overflow case against headless pixels. They also check draw counts, texture
reuse and upload-ring wraparound over repeated frames. A timing smoke check
requires finite GPU phases after a completed readback frame, and a copy-area
check verifies that small translucent shapes do not copy the entire target.
Another pixel test covers 100 disjoint translucent rectangles in two batches,
mixed rectangles and triangles across clip boundaries, overlapping shapes
that must flush, stroked rectangles, 48 varied overlapping lines and 32
overlapping rounded rectangles. The
readback path is a private test hook; ordinary frames do not allocate it.
A separate Windows widget regression builds a layout-arranged panel with button,
checkbox, toggle and slider, adds rasterized text to the button, and compares
the resulting context command stream with headless pixels for idle and clicked
frames in light, dark and high-contrast themes.
The [D3D12 benchmark](../../benchmarks/d3d12_bench.c) records end-to-end wall
time for four local scenes. The wall-clock numbers include vsync; alpha and
bitmap scenes also include a per-frame fence wait. The benchmark separately
prints min/median/max GPU timings from distinct completed frames when timestamp
queries are available. These local samples are not a frame-time guarantee.
A Win32/F11 integration test sends a synthetic DPI-change message, checks the
1.5× logical-to-physical mapping, suspends a zero-size target, resizes the swap
chain and compares GPU pixels with headless output after device recovery where
removal is supported. An actual move between monitors and cross-adapter
recovery remain to be tested.
