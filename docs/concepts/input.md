# Input and frame transitions

NexaUI uses a backend-neutral `nx_event` stream. Native window backends translate OS messages into logical coordinates, key names, pointer buttons, touch contacts, wheel units, Unicode scalar text, focus and resize events. A window's event queue preserves order, except consecutive mouse pointer moves are coalesced to the newest position. Win32 implements the full current input set, UTF-8 plain-text clipboard and filesystem drops. The Linux/X11 adapter implements mouse, wheel, basic key/text, focus and resize events, clipboard transfer and local-file drops. It accepts committed UTF-8 from an optional XIM context; the keysym fallback still has limited keyboard-layout coverage. The initial Wayland adapter implements pointer buttons, movement, scroll, focus, basic XKB key/text, key repeat, cursor shapes, resize events, UTF-8 clipboard transfer and local-file drops. Optional text-input-v3, or v1 as a fallback, accepts committed UTF-8 when enabled for a focused editor; the text-field widget manages this when given `ime_window`, and custom editors can use the activation API directly. Preedit from Windows, X11 callback-style XIM, and Wayland v3/v1 is available to focused text fields; macOS preedit remains pending. macOS remains planned.

Applications call `nx_window_poll` on a window's creation thread. On Win32, one poll dispatches messages for every window on that thread into each window's own queue. Call `nx_window_route_events(window, context, &count)` for each window/context pair before its next frame; use one independent context per window. The transfer keeps an event queued if the context cannot accept it, so the same pair can retry after a context allocation failure. `count` reports events already transferred, and the caller must avoid routing the remainder into a different context if ordering matters. For manual dispatch, repeatedly call `nx_window_next_event` until `available` is zero and queue each event with `nx_context_queue_event`; unlike the route function, a popped event is then the caller's responsibility. The next `nx_begin_frame` swaps the pending queue into a frame-local stream and updates the input snapshot. Events queued during an active frame belong to the next frame. The borrowed array from `nx_frame_events` stays valid until the next begin or context destruction.

The X11 adapter opens one X display connection per window. Poll each window before routing its events. It requests detectable key repeat where supported, maps native buttons and basic key symbols, publishes UTF-8 titles through `_NET_WM_NAME`, and honors `WM_DELETE_WINDOW` without destroying the window before the caller releases it. When XIM is available for the process locale and `XMODIFIERS`, it filters native events and emits committed UTF-8. It retains its earlier preedit-spot context and switches focused editors to a separate callback context when the input method advertises that style. A missing or incompatible XIM context falls back to basic key lookup. The clipboard uses the X11 `CLIPBOARD` selection and `UTF8_STRING` target, responds to `TARGETS`, and pumps windows on the same UI thread while waiting for a text conversion. Direct properties and incremental `INCR` transfer work in both directions. Text is capped at 32 MiB, and at most four outgoing incremental transfers run per window. Xdnd version 5 advertises local-file copy drops, accepts `text/uri-list`, receives direct or `INCR` selection data and sends `XdndFinished` after queueing paths. The X11 callback context exposes bounded preedit for focused editors when that XIM style is advertised; installed-IME acceptance and monitor DPI remain pending.

The Wayland adapter opens one connection per window, discovers `wl_compositor`, `wl_shm`, `wl_seat`, `wl_output`, `wl_data_device_manager` and `xdg_wm_base`, and maps a visible xdg-shell toplevel after its first configure. It receives pointer coordinates/buttons/axes from `wl_pointer` and parses the compositor's XKB keymap for logical keys and basic Unicode scalars. The compositor's repeat rate and delay drive a bounded local timer; key release, keymap changes and focus loss cancel it. When `zwp_text_input_manager_v3` is advertised, the application can enable text input for a focused editor, set its logical caret rectangle, and receive committed UTF-8 after the protocol's `done` event. If v3 is absent, the adapter uses `zwp_text_input_manager_v1` when available. It suppresses duplicate XKB text while the protocol handles the editor and resumes XKB text when deactivated. The v3 path exposes preedit text after `done`, while v1 exposes it after `preedit_string`; both queue `NX_EVENT_IME_PREEDIT_CHANGED` for redraw; focused text fields insert and underline it visually without changing the committed draft. Focused ordinary text fields send a UTF-8 slice of at most 4000 bytes containing their complete selection. V3 queues valid selection-relative deletion after `done`; v1 queues valid cursor-relative deletion with the following `commit_string`. Both place deletion before tagged text and apply it only to the matching editor revision. An oversized selection sends empty context while preserving the editor identity. Eleven cursor shapes are drawn into owned ARGB shared-memory buffers and submitted on pointer entry or a shape change. The integer backing scale follows the largest scale of the outputs entered by the surface; a scale change emits a resize event with unchanged logical dimensions, replaces the shared-memory background and scales cursor pixels. Output removal returns the surface to its remaining output scale, or 1 when none remain. Clipboard ownership uses a pointer-button or keyboard-key serial and serves UTF-8 from nonblocking pipes; incoming offers are read through a bounded pipe with same-thread window pumping. A `text/uri-list` drop accepts local `file:` paths, percent-decodes them and queues the batch with release coordinates. Fractional scaling remains pending.

`nx_frame_input` reports pointer position, accumulated wheel deltas, held/pressed/released button masks, current modifiers and focus. `nx_key_down`, `nx_key_pressed` and `nx_key_released` report the same distinctions for keys. Pressed/released flags reset each frame. A press and release within one frame sets both flags while the held state is false. Focus loss releases held keys and buttons to avoid a stuck input state. A key repeat produces another event but does not become a fresh press while the key is already held.

The application may choose a client-area cursor for each native window with `nx_window_set_cursor`. The showcase sets a crosshair over its plot and restores the default elsewhere. On Windows, the adapter handles [WM_SETCURSOR](https://learn.microsoft.com/en-us/windows/win32/menurc/wm-setcursor) for the client area, leaving non-client cursors to the OS. Shared system cursor resources require no application-owned destruction. Cursor choice is window state; it is not part of the normalized input event stream.

Wheel events also route to the innermost registered `NX_REGION_SCROLLABLE` viewport under the pointer. Its `nx_interaction_state.wheel_x/y` accumulates only the deltas delivered to that region; a child button does not consume the wheel. `nx_scroll_area_begin` uses these deltas to update caller-owned offsets and clip its children.

Touch events carry `contact_id` and logical client coordinates independently of mouse state. The Win32 backend handles [WM_POINTER touch messages](https://learn.microsoft.com/en-us/windows/win32/inputmsg/wm-pointerdown), converts screen pixels to client logical units, and emits cancellation on [pointer capture loss](https://learn.microsoft.com/en-us/previous-versions/windows/desktop/inputmsg/wm-pointercapturechanged). The first active contact can drag a scroll area after eight logical pixels of movement. A shorter touch released over the original interactive target produces its click and focus state, including controls outside scroll areas. A long drag, a release over another target or cancellation does not click. Multi-touch gestures and touch dragging of controls remain pending.

Keyboard events identify logical keys. Text input is separate and carries Unicode scalar values; widget editing must consume text events rather than infer characters from key names. The Win32 path combines UTF-16 surrogate pairs from `WM_CHAR` and emits U+FFFD for malformed pairs. When a focused ordinary text field selects in-field composition, Windows IMM preedit is copied from `GCS_COMPSTR`, converted to UTF-8 with a byte cursor, and displayed without changing the draft. Start, end, result and focus loss clear it. Native candidate UI remains available, and committed characters continue through `WM_CHAR`. Other fields use the default IME composition window. Clause styling and candidate choices are not exposed; acceptance with an installed non-Latin IME remains open.

`nx_window_clipboard_set_text` publishes validated UTF-8 as `CF_UNICODETEXT`; `nx_window_clipboard_get_text` reads it into caller-owned UTF-8 memory. Both run on the window's creation thread. Clipboard line endings use CRLF on Windows and LF in returned UTF-8. `nx_text_buffer_selected_span` supplies a borrowed selection for copy, and `nx_text_buffer_replace` accepts pasted bytes. For the general text field, set its optional clipboard callbacks (or fill them with `nx_text_clipboard_for_window`) to enable Ctrl+C/X/V. Custom editors and the numeric field still handle clipboard shortcuts themselves.

`nx_window_next_file_drop` reads one UTF-8 filesystem path at a time from a separate per-window queue. Query the required byte count with a null destination; a short buffer leaves the path queued for retry. Each path carries its zero-based index, batch count and logical client coordinates. Win32 receives [WM_DROPFILES](https://learn.microsoft.com/en-us/windows/win32/shell/wm-dropfiles), converts the whole batch before queuing it, and releases the native transfer handle after processing. A failed allocation leaves that batch unqueued and makes `nx_window_poll` report a sticky error. This path does not receive virtual files or arbitrary drag payloads, and its separate queue does not express ordering relative to normalized input events.

Event queues grow with the configured allocator. The context reuses two buffers across frames; after warmup, ordinary frames need no event-buffer allocation. Allocation failure returns an error and preserves already queued context events. The Win32 queue reports a sticky allocation error if it cannot retain an OS event, because silently dropping a release could leave an invalid interaction state. Applications should treat this as a window failure and rebuild the affected input context.
