# Layout contract

NexaUI uses a deterministic measure/arrange algorithm in logical pixels. Rows, columns, wrapping rows/columns, overlays, grids, split panes, scroll containers and leaves are implemented in the standalone `nx_layout` tree. A separate height index supports virtual list ranges.

## Constraints and sizes

Each axis receives an available interval `[0, max]`, where `max` may be unbounded. A node has finite nonnegative minimum and preferred values and a maximum that is finite or positive infinity, with `min <= max`. Preferred size is clamped to that interval. Invalid or NaN inputs produce an explicit error before changing the layout tree. No implicit negative size is allowed. Intermediate sums use double precision even though public geometry is float; results outside float range return `NX_ERROR_LIMIT`.

Measure returns the smallest desired size that honors the node's own constraints after measuring children. Arrange receives a final rectangle and produces a rectangle for every visible child. Arrange may assign less than the measured preferred size when the parent is constrained, but must not violate a child's minimum unless the parent's inner space is smaller than the sum of minimums. In that impossible case, content overflows and is clipped or scrolled; child sizes do not become negative.

The layout engine never rounds logical coordinates to integer pixels. Renderers snap or sample at their own backing scale. This avoids cumulative DPI drift. All layout traversals use stable child order.

## Box model

Each node has content, padding, border and margin. Padding and border belong to the node and count toward its measured size. Margin belongs to the parent's spacing computation and does not expand the child's reported content size. The parent's available inner rectangle is its arranged rectangle minus its border and padding. Adjacent margins do not collapse. Parent gap is added between child margin boxes, including zero-size children. Omission from layout is not implemented yet.

## Row and column

A row's main axis is horizontal; a column's is vertical. Measurement adds child outer preferred sizes and `gap * (n - 1)` on the main axis and takes the maximum child outer preferred size on the cross axis. Padding and border are then added. Cross-axis stretch is opt-in; otherwise children use their measured cross size and are aligned start, center or end.

During arrangement, subtract fixed child preferred sizes, margins and gaps from the available main span. Positive free space is distributed among children with positive grow weights in proportion to weight, capped by each maximum; redistribute remaining space until no eligible child remains. Negative free space is removed among children with positive shrink weights in proportion to `shrink_weight * preferred_size`, stopping at minima and redistributing any remainder. If minima still exceed available space, preserve minima and allow overflow. Equal-weight ties resolve by source order and deterministic floating-point rules. An unbounded main axis does not trigger growth.

Auto sizing uses intrinsic child measurements. A leaf without an explicit preferred size has intrinsic size zero until a future widget/text measurement callback supplies one. A fixed size uses the specified preferred size clamped by min/max. A flexible size participates in grow/shrink with a preferred basis. Percentages are not implemented yet; their eventual behavior must avoid recursive dependency cycles.

## Overlay, grid and wrapping

An overlay measures the maximum outer child width and height. It arranges each child within the same inner rectangle using its alignment and constraints. Z-order follows child order; hit testing walks the opposite order. Clipping is independent of z-order.

`NX_LAYOUT_GRID` uses explicitly configured column and row tracks. Configure at least one track on each axis with `nx_layout_grid_configure` before adding children; it copies the arrays. Add children with `nx_layout_add_grid`, using zero-based row/column positions and positive spans. Overlapping children retain source order. `gap` is the horizontal gap and `line_gap` is the vertical gap, including inside a span.

Fixed tracks start at their requested size clamped by minimum and maximum. Auto and flex tracks start at their minimum. Children in fixed-only spans are measured with that finite span; others first receive unbounded space for intrinsic measurement. Single-track contributions are applied before spanning children, each in source order. If a child needs more space than its tracks and interior gaps provide, the deficit is divided equally among auto tracks in its span, redistributing when a maximum is reached. Remaining deficit is divided among flex tracks in the same way. Fixed tracks never grow from content; content may overflow if all eligible tracks reach their maxima. For example, two auto tracks with maxima 4 and infinity, a gap of 1 and a child spanning both that needs 21 resolve to widths 4 and 16.

On a finite measured width, flex columns divide spare space by positive `value` weight, capped at their maxima; children are then measured again at their resolved column span so wrapping can determine row heights. Auto rows receive intrinsic height from those children. The grid reports its base track extents as desired size. At arrangement, flex tracks consume extra space; if space is short, flex tracks then auto tracks shrink toward their minima. Fixed tracks stay fixed. Children align or stretch within their final cells using their own margins and axis constraints. Re-measure when the intended width changes enough to affect nested content.

`NX_LAYOUT_WRAP_ROW` and `NX_LAYOUT_WRAP_COLUMN` choose greedy line breaks during measure from the available inner main-axis maximum. A child wider or taller than the limit occupies its own line. Margins count toward line breaks; `gap` separates children in one line and `line_gap` separates lines. Arrangement preserves the measured breaks even if its assigned rectangle differs. Main-axis grow/shrink is distributed independently per line, while cross-axis alignment uses each line's tallest or widest child. Re-measure with new constraints to recompute breaks.

## Split panes

`NX_LAYOUT_SPLIT` owns exactly two children. `split_axis` selects side-by-side or top-and-bottom layout; `gap` is the divider thickness. The default is a horizontal split at ratio 0.5 with a six-pixel divider. Measurement adds the children's outer preferred sizes and the divider on the main axis, and takes their maximum outer size on the cross axis. `nx_layout_set_split` updates the first pane's requested fraction and invalidates arrangement without requiring a new measure. `nx_layout_get_split_info` returns the divider rectangle and effective outer pane extents after arrangement.

Arrangement first removes the divider from the inner main-axis size. It clamps the used pane space to the sum of child minima and maxima, including margins. The requested first-pane fraction is then clamped to bounds that keep both panes within those limits. If the minima exceed available space, both minima are preserved and the second pane overflows. If both maxima use less than the available space, unused space follows the second pane. Cross-axis alignment and stretching use each child's normal axis rules.

`nx_splitter` takes the arranged `nx_split_info`, an axis, a stable widget ID and a caller-owned ratio. It paints a divider, captures pointer drags and supports Left/Right for horizontal splits or Up/Down for vertical splits, plus Home/End. The optional keyboard step defaults to 0.05. The semantic separator exposes its numeric ratio and increment/decrement/set-value actions. The caller applies a changed ratio with `nx_layout_set_split` and arranges the next frame. Both pointer and keyboard changes start from the **effective** ratio, so child constraints cannot cause a jump when the requested ratio differs from the visible split. The call commits the ratio only after registration and painting succeed.

## Docking model

`nx_dock_model` is a caller-buffer tree of split nodes and tab stacks. Each split stores an axis, a requested ratio and two child IDs; each stack stores a selected panel ID. `nx_dock_tab` entries associate stable panel IDs with stacks, and their array order defines tab order within a stack. `nx_dock_init` creates the first stack and panel. `nx_dock_split` adds a sibling stack around an existing stack, `nx_dock_add_tab` adds a panel to a stack, `nx_dock_move` appends a panel to another stack and selects it, and `nx_dock_select` changes selection. A move cannot leave an empty stack. The application maps split nodes to `NX_LAYOUT_SPLIT` and stack nodes to tab controls, using its own panel content.

`nx_dock_validate` checks unique node and panel IDs, parent/child consistency, acyclic reachability from the root, valid ratios, nonempty stacks and valid selections. Mutating operations reject malformed models. `nx_dock_encode` writes a stable little-endian v1 snapshot, or reports its required size when passed a null destination. The format starts with `NXDK`, a version, node and tab counts and the root ID, followed by fixed-size node records and ordered tab records. Ratios are stored as IEEE-754 binary32 bits. `nx_dock_decode` requires an exact size, rejects malformed structures and clears model counts/root on failure. The caller's node/tab buffers remain allocated and may be reused. The model provides structure and persistence; visual docking previews and pointer drop targeting remain application work.

The [docking editor example](../../examples/10_docking_editor/README.md) connects this model to tab widgets and a draggable splitter, then saves and verifies a v1 snapshot.

## Scroll and virtualization

A scroll container owns at most one content child. Its `scroll_axes` mask selects horizontal, vertical or both axes; the default is vertical. It measures the child with unbounded space in those axes, but bounds its own desired viewport by finite available space. `nx_layout_set_scroll` stores a nonnegative requested offset and invalidates arrangement. Arrangement clamps that offset to the child margin-box extent minus the viewport. `nx_layout_get_scroll_info` returns the viewport, content extent and effective offsets after arrangement. The caller pushes `info.viewport` with `nx_push_clip` while drawing and registering interactive content, then pops it. Nested clips also restrict hit regions; content coordinates are already translated by arrangement.

`nx_scroll_area_begin` provides the interactive viewport around that geometry. Give it the viewport, measured content extent, axes and caller-owned offsets before arranging the content. It routes wheel input to the innermost scrollable region under the pointer, clamps offsets, paints the viewport and pushes a clip. Apply its returned offsets with `nx_layout_set_scroll`, arrange, register and paint children, then call `nx_scroll_area_end`. The end call draws scrollbar thumbs above the children. The scroll-area clip must be the top clip when it ends; `nx_end_frame` rejects an unclosed scroll scope. Wheel units move 40 logical pixels by default, configurable through `wheel_step`. Disabled areas do not consume wheel input. A begin failure rolls back the semantic node, region and commands without changing the offsets; a failed end call can be retried in the same frame.

Set `thumb_x_id` or `thumb_y_id` to a unique, nonzero widget ID to make that axis's thumb draggable and keyboard focusable. The corresponding scroll axis must be enabled. Dragging maps thumb travel to the full content offset and retains pointer capture outside the track. A focused vertical thumb accepts Up/Down, Page Up/Down, Home and End; a focused horizontal thumb accepts Left/Right, Page Up/Down, Home and End. Arrow keys move by `wheel_step` (40 by default), page keys by one viewport, and Home/End to the limits. The thumb is exposed as a child slider semantic with its current percentage. A zero thumb ID keeps the visual bar and wheel scrolling, without a focusable thumb. Disabling the area also disables thumb input and removes its keyboard focus.

Touch contacts use `NX_EVENT_TOUCH_DOWN`, `MOVE`, `UP` and `CANCEL` with a stable `contact_id` and logical coordinates. The first active contact over a scroll area binds to the innermost enabled scroll viewport. Once it travels eight logical pixels, dragging the finger moves content in the opposite direction on each enabled axis, even if the finger leaves the viewport. A shorter touch released over its original child widget activates and focuses that widget without moving the scroll area. A second contact does not alter the active gesture. Up, cancel, focus loss, removal or disabling of the area ends the binding. Touch events do not change mouse button or hover state. The Win32 adapter translates `WM_POINTER` touch messages and pointer-capture loss into these events; inertia and control-specific touch drags remain separate work.

`nx_virtual_list` stores positive per-row heights in a Fenwick index. `nx_virtual_list_range` returns a half-open visible range, its first row's content offset, total extent and clamped viewport offset in logarithmic time; `nx_virtual_list_offset_at` positions an instantiated row. Overscan is capped at 256 rows on each side, so a request cannot accidentally instantiate a million rows. Individual height updates are logarithmic and leave the index unchanged on error. The application should assign stable row IDs from its data keys and instantiate only the returned rows.

`nx_virtual_list_rebuild` handles a changed row set. The application callback supplies a unique nonzero key and measured positive height for each new row. The list initially uses keys `index + 1`; rebuild with application keys before relying on identity across reorderings. Rebuild captures the currently visible row from the old key order and adjusts the caller's offset so the same key remains at the same pixel position after insertion, removal, reordering or a height change before it. If that key disappears, it keeps the old absolute offset within the new scroll limits. The callback runs once per row; rebuilding takes linear time and temporary memory, so `nx_virtual_list_set_height` remains the choice for a single unchanged row. Invalid keys, heights, callbacks and allocation failures preserve the previous index and offset. The application still owns the actual row widgets and calls `nx_virtual_list_range` or `nx_virtual_list_visit` again after rebuilding.

`nx_virtual_list_visit` can instantiate the returned rows directly. Its callback receives each visible or overscan row's stable key, index, height, content Y and viewport-relative Y in order. Use a widget ID derived from the key (or the key itself when globally unique in the context) under the scroll area's semantic parent, and add the viewport origin to `viewport_y` for drawing. A required `max_rows` budget is checked before any callback, including when tiny rows make many rows fit in one viewport. The visitor allocates nothing and reports how many callbacks succeeded; callback side effects already performed remain the application's responsibility if a later callback fails. The callback must not mutate the list during traversal.

## Caching and invalidation

The current tree is rebuilt with `nx_layout_reset`, which reuses its node buffer. A successful measure remains valid until the next add, reset or measure call. Arrangement requires a successful measure of the same root; only nodes in that arranged root may be queried. Retained widget identity, incremental measure caching, style/content version keys and layout diagnostics are future tasks. UI-specific caches will belong to the context; application domain state will not. Tests cover nested finite/unbounded constraints, impossible minima, empty containers, allocator failure and malformed numeric inputs; DPI changes and deep-tree stress remain to be expanded.
